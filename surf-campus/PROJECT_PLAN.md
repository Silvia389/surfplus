# SURF Campus 数据驱动项目规划书

> 项目：XJTLU Virtual Campus / SURF Campus
> 规划依据：问卷 50 份、线上采访汇总、问卷 AI 分析报告、现有前后端代码
> 版本：Requirements Plan v1.0
> 日期：2026-07-31

## 1. 规划目标

把 SURF Campus 从“有很多页面的 Demo”推进成一个真正能解决校园问题的产品。

本项目不以“把所有功能都做出来”为第一目标，而以用户是否能顺利完成任务为目标。每一轮开发都要交付一条完整的功能链：

```text
用户目标 -> 入口 -> 数据/匹配 -> 操作 -> 结果反馈 -> 后续行动
```

## 2. 研究结论

### 2.1 样本和限制

- 问卷有效样本：50 份
- 大一学生占 74%，理工/计算机占 50%，商科/管理占 32%
- 教职工访谈材料主要来自就业办两位老师
- 因此，学生需求结论较强，但高年级、教职工和国际生需求仍需要后续补充验证

### 2.2 最强痛点

| 用户问题 | 数据证据 | 产品含义 |
|---|---:|---|
| 信息分散，需要在多个平台切换 | 35/50，70% | 必须有统一入口和全局搜索 |
| 重要通知被淹没 | 24/50，48% | 必须有通知分级、置顶和提醒 |
| 找不到队友或学习伙伴 | 21/50，42% | 必须从“发帖等回复”升级为主动匹配 |
| 找不到资料或历史信息 | 20/50，40% | 必须建设结构化资料库和问答沉淀 |
| 匿名环境中的攻击和不良内容 | 13/50，26% | 匿名功能必须和审核、举报、追溯一起设计 |
| 界面复杂、操作不便 | 9/50，18% | 首页必须降低层级和寻找成本 |

### 2.3 最想完成的场景

| 用户场景 | 选择人数 | 优先级 |
|---|---:|:---:|
| 查找学习资料 | 37/50，74% | P0 |
| 寻找队友与学习伙伴 | 32/50，64% | P0 |
| 向老师、助教或前辈提问 | 29/50，58% | P0 |
| 获取班级和活动通知 | 27/50，54% | P0 |
| 校内话题讨论与活动 | 27/50，54% | P1 |
| 前辈经验与申请规划 | 24/50，48% | P1 |
| 校内技能和资源互助 | 17/50，34% | P1 |
| 情感支持与心理放松 | 10/50，20% | P1 |

### 2.4 功能意愿和体验底线

- 学术讨论区平均 4.26/5
- 师生互动专区平均 4.26/5
- 组队功能平均 4.22/5
- 跨年级、跨专业认识同学平均 4.14/5
- 活动日历和报名平均 4.12/5
- 智能推荐平均 4.08/5
- 界面清晰易懂平均 4.40/5
- 容易学会使用平均 4.34/5
- 找信息不费力平均 4.36/5
- 56% 偏好校园超级 App，44% 偏好模块化界面
- 40% 的用户会因广告泛滥放弃平台，24% 会因卡顿或闪退放弃，20% 会因社区氛围差放弃
- 39/50 对广告完全不接受或不太接受

### 2.5 采访补充出的关键要求

- 学术内容与日常社交必须有清晰边界，不能互相淹没
- 用户希望通过专业、技能、兴趣标签找到科研项目、比赛队友和学习伙伴
- 教职工需要更高效地发布科研、志愿者和助理招募，并获得报名反馈
- AI 应该减少查询和整理成本，但不能伪造学术来源或代替人工兜底
- 匿名适合课程困惑、后勤反馈和情绪表达；科研组队、资源交易等高信任场景应优先实名
- 校园社区应尽量隔绝商业推广，保留真实的师生分享
- 界面要简洁、现代、少层级，不能做成复杂的教务系统

## 3. 产品北极星目标

### 北极星目标

让一个西浦学生在进入平台后的 3 分钟内，完成至少一个真实校园任务，并且不需要在多个平台之间来回切换。

### 第一版成功标准

用户可以从“一页校园工作台”完成以下至少 6 个动作：

1. 查看重要通知
2. 查看近期课程任务或考试
3. 搜索并打开一份课程资料
4. 提交一个课程问题
5. 找到一个匹配的队友或项目
6. 查看并报名一个校园活动
7. 向 AI 提问校园或学习问题

## 4. 体验重建与设计执行标准

### 4.1 重建原则

现有 Demo 的视觉、组件和交互不作为新版本的设计基础。SURF Campus 不做“把功能堆进模板页面”的校园门户，而是从用户任务、信息优先级和操作反馈重新设计整个体验。

新界面应让学生感到**清楚、平静、可靠、可掌控**：重要事情一眼可见，下一步无需猜测，操作立刻得到反馈。学术、通知、社区和匿名内容保持明确边界，不用夸张装饰、通用营销式卡片或无目的动画掩盖信息层级问题。

### 4.2 强制设计与交互方法

从信息架构、线框、组件、动效到验收，全部持续使用以下两套 Skill 作为设计判断标准：

- **Apple Design**：以目的、掌控感、责任、熟悉性、灵活性、简洁、工艺和愉悦感检查每一个用户路径；强调即时反馈、空间一致性、可中断交互、可访问性和尊重用户隐私。
- **Emil Kowalski / Design Engineering**：以优秀默认值、组件一致性、克制而有目的的动态效果、可感知的性能和细节打磨作为实现标准；每个组件都要处理常见状态与边界情况，而不是只完成静态正常态。

这不是在开发完成后补一次“视觉优化”。每次开始一个 Goal 前，先用两套 Skill 检查任务路径；实现后再用它们复核视觉层级、交互反馈、动态行为与响应式表现。

### 4.3 界面方向

- 以“校园工作台”而非社交信息流为首页模型：当前最重要的任务、通知、课程和活动优先，次要探索内容后置。
- 建立统一的应用 Shell、导航、页面标题、搜索、反馈、表单、列表、详情和操作组件；不沿用旧 Demo 的临时拼接式样式。
- 用清晰的排版、留白、分组、对比和图标表达层级。卡片只用于真正独立、可重复的内容单元，不把整个页面切成漂浮卡片墙。
- 色彩、字体、间距、圆角、阴影、状态色和图标建立为可复用 token；默认使用系统字体并适配用户的文字缩放。
- 桌面端支持快速扫描、搜索和高信息密度；移动端优先保证单手可达、触控目标、底部导航和内容连续性。两端共享任务模型，但不机械缩放同一个布局。
- 每个页面都必须回答：我在哪里、最重要的事是什么、我下一步能做什么、如何返回或取消。

### 4.4 交互与动效标准

- **先判断是否需要动画**：高频操作、键盘触发和纯信息切换不增加延迟；动效只用于状态反馈、空间关系、避免突兀变化或帮助理解。
- 所有可点击控件在按下时立即反馈；加载、完成、警告和错误状态必须清晰且贴近触发操作。
- 弹层、菜单、抽屉和详情回退保持空间一致：从触发位置出现，并沿合理路径关闭或返回。可拖拽的表面应支持指针捕获、边界阻尼、速度延续和中途反向。
- 常规 UI 动效以短、快、克制为默认；进入使用明确的 ease-out，屏幕内移动使用 ease-in-out。只有用户带来动量的拖拽或甩动才使用轻微弹性。
- 动画优先使用 `transform` 和 `opacity`，避免为装饰而造成布局抖动或降低加载性能；动态 UI 支持中断和重新定向。
- 支持 `prefers-reduced-motion`、`prefers-reduced-transparency` 和更高对比度需求。减少动态不等于去掉反馈，应以短暂淡入淡出或静态状态替代大幅位移动画。
- 悬停效果只在精细指针设备启用；键盘操作、焦点状态、触屏状态和错误恢复都与视觉设计一起完成。

### 4.5 设计验收门槛

一个 Goal 除了功能闭环外，还必须满足：

1. 先完成可交互原型或可运行界面，再确定视觉细节。
2. 所有入口、加载、空数据、失败、成功、禁用和返回状态使用统一组件和明确文案。
3. 关键路径在桌面端和移动端实际走通；没有文字截断、控件遮挡、无效点击或依赖悬停才能发现的操作。
4. 为所有新增或改造的动效记录目的、触发条件、时长/弹簧参数和减弱动态策略；无法说明目的的动效不进入产品。
5. 使用 Apple Design 与 Emil Kowalski / Design Engineering 的标准做一次实现后复核，并记录发现的问题和修正结果。

## 5. 核心产品结构：校园话题首页 + 任务入口

首页的主要内容必须是可连续阅读、可讨论、可检索的校园话题流，而不是一组工作台卡片或以图片为中心的瀑布流。校园用户以文字表达、课程提问和信息交换为主，因此内容流优先保证阅读顺序、上下文、分区与搜索效率；通知、课程资料、问答、活动、组队和 AI 是清晰可达的任务入口与内容内行动，不抢占内容流作为首页主体。

首页信息结构：

```text
顶部：全局搜索 + AI 问答入口 + 未读通知
快捷区：重要通知 / 今日任务 / 课程资料 / 活动 / 组队等低干扰入口
主区：单列校园话题流（默认推荐，可切换关注、学术、校园生活、活动机会、组队项目等内容范围）
侧栏/移动二级入口：重要通知、热门标签、相关资料与活动
帖子内：作者/匿名状态、文字优先的内容、可选图片或视频、标签、互动、收藏、评论、问 AI、相关行动
底部：首页、学术、发布、活动、通讯、个人中心
```

首页入口和内容流需要支持：

- 按年级、专业和兴趣进行初步个性化推荐
- 内容范围筛选、标签聚合和加载更多，不让学术、普通社交和匿名内容无边界混杂
- 将帖子和快捷入口直接连接到详情页或动作页
- 统一显示加载、空数据、失败和已完成状态

### 首页内容流与发布要求

- 首页采用**单列话题流**：桌面端以舒适阅读宽度的主列为核心，侧栏显示通知和热门标签；移动端维持单列连续阅读。图片和视频按原始合理比例显示，但不改变文字帖的阅读顺序。
- 用户可以发布纯文字、图文帖子和视频帖子；发布器默认聚焦文字输入，图片和视频是可选附件，不让“有媒体”成为参与讨论的门槛。
- 图片需要支持多张预览、排序、删除、上传进度、失败重试和详情查看；视频需要显示封面、时长、加载状态、播放/暂停、静音和失败反馈。
- 帖子卡片和详情页按内容类型设计，不把视频、图片和文字强行塞进同一种固定样式。纯文字帖子保持易读层级，图片与视频保持正确比例与可查看性。
- 每篇帖子必须属于一个受控分区：学术、校园生活、活动与机会、组队与项目；匿名树洞独立进入，不与实名公共内容默认混流。分区是内容边界，不是单纯颜色标签。
- 每篇帖子可添加 0-5 个标签。优先提供课程、活动、技能、地点、议题等推荐标签，也支持审核后的自定义标签；点击标签进入聚合页，查看同一标签下的帖子、课程问答、资料、活动和相关标签。
- 全局搜索应聚合检索帖子标题/正文/标签/分区、课程资料、问答和活动；搜索结果按内容类型分栏与筛选，并可从标签或关键词继续探索相关议题。
- 发布、媒体上传和浏览必须与匿名选择、社区分区、举报、审核和内容状态一起设计；未审核、隐藏、撤回或处理中的内容在学生端和管理端呈现清晰、不同的状态。

双列瀑布流不用于首页主内容。未来如需图片和视频导向的“发现”页，可以作为独立探索视图，不能替代文字讨论和信息交换的主话题流。

## 6. 目标模式执行地图

### Goal A：我不再错过重要校园信息

**用户目标**：快速知道今天有什么必须处理的事。

**功能集合**：

- 统一通知中心
- 通知来源分类：课程、活动、教务、招募、系统
- 重要通知置顶
- DDL、考试和活动时间线
- 已读、未读、稍后处理和免打扰
- 通知搜索与筛选

**完整路径**：

`工作台 -> 重要通知 -> 查看详情 -> 标记处理/加入日程 -> 收到提醒`

**完成标准**：重要通知可以被单独识别；用户能在 10 秒内找到未读事项；通知不会和普通动态混在一起。

### Goal B：我能找到资料并得到答案

**用户目标**：不用翻几百人的聊天记录，就能找到课程资料和可靠回答。

**功能集合**：

- 按课程、类型、学期和关键词搜索资料
- 资料详情、预览、下载和收藏
- 课程问答区
- 问题标签、回答、采纳和历史沉淀
- 教师、助教和前辈身份标识
- AI 摘要、相关资料推荐和答案来源提示

**完整路径**：

`工作台 -> 搜索课程/资料 -> 打开资料 -> 继续提问 -> 查看回答和相关内容`

**完成标准**：资料可检索、可打开、可收藏；问题可发布；AI 回答必须标明“参考资料/可能不准确”，关键学术问题支持人工答案入口。

### Goal C：我能找到合适的队友和项目

**用户目标**：从“发一个帖子等别人看”变成主动找到合适的人。

**功能集合**：

- 技能、专业、年级、语言和兴趣标签
- 项目/比赛/科研/志愿者招募
- 招募需求、截止时间、人数和角色
- 推荐队友和推荐项目
- 一键申请、发起聊天和报名状态
- 实名优先的高信任模式

**完整路径**：

`工作台 -> 组队推荐 -> 查看项目 -> 查看成员需求 -> 申请/聊天 -> 形成队伍`

**完成标准**：用户可以发布招募、填写技能、查看匹配理由、申请加入并收到状态反馈。

### Goal D：我能参加真实的校园活动

**用户目标**：看懂活动重点，快速判断是否参加并完成报名。

**功能集合**：

- 活动日历和列表
- 活动分类、时间、地点、组织方和名额
- 精简版活动卡片，重点信息前置
- 一键报名、取消报名和报名状态
- 活动提醒和相关内容推荐
- 教职工/管理员一键发布招募

**完整路径**：

`工作台 -> 活动卡片 -> 查看重点 -> 报名 -> 加入日程 -> 收到提醒`

**完成标准**：用户无需阅读长文即可理解活动时间、地点、对象和报名状态。

### Goal E：我可以表达，但平台值得信任

**用户目标**：在需要时匿名表达，同时不被攻击、骚扰或泄露信息。

**功能集合**：

- 单列话题内容首页、受控分区和内容范围筛选
- 纯文字、图文和视频发布器
- 课程/活动/技能/议题标签、标签聚合页和聚合搜索
- 图片/视频预览、上传进度、失败重试和详情查看
- 场景化匿名开关
- 匿名发帖和匿名提问
- 社区规范和发布前提示
- 举报、屏蔽、审核和内容状态
- 后台可追溯但前台不暴露实名
- 高信任场景强制或优先实名

**完整路径**：

`选择板块 -> 选择文字/图片/视频 -> 选择实名/匿名 -> 发布与上传 -> 审核/展示 -> 评论、举报或屏蔽`

**完成标准**：用户能发布、浏览并打开文字、图文和视频内容；首页以单列话题流清晰呈现文字讨论和媒体内容；用户能通过分区、标签和聚合搜索发现相关议题；用户清楚知道匿名范围；匿名不是无责任；违规内容有处理状态；举报后有反馈。

### Goal F：AI 帮我减少查询和整理成本

**用户目标**：在我正在看的内容旁边直接询问 AI，而不是离开当前内容后重新描述问题。

**功能集合**：

- 帖子详情中的“问 AI 这篇内容”
- 评论旁的 `@AI` 入口，自动带入帖子和评论上下文
- 全局搜索中的“搜索内容 / 问 AI”切换
- 自动识别学术、校园事务、活动和社交问题
- 基于现有校园数据回答
- 资料和通知自动摘要
- 相关链接、活动和联系人推荐
- 不确定性提示、来源展示和人工兜底
- 对话历史和清除记录

**完整路径**：

`帖子/评论/搜索结果 -> @AI 或问 AI -> 返回带上下文的答案和来源 -> 打开相关资料/通知/活动 -> 完成行动`

**完成标准**：AI 不只返回文字，还能理解当前帖子、评论或搜索结果；用户不需要重复复制上下文；缺少依据时明确说明；涉及政策、成绩和重要学术内容时不能伪造结论。

### AI 交互原则

AI 是“内容旁边的操作”，不是一个脱离场景的孤立页面。

- **帖子级提问**：用户可以询问“这篇帖子在说什么”“帮我总结重点”“这件事和我有什么关系”。
- **评论级提问**：用户可以在某条评论旁 `@AI`，询问“这个回答靠谱吗”“帮我解释这句话”“把这条建议整理成行动清单”。
- **搜索级提问**：用户输入关键词后，可以选择普通搜索，也可以让 AI 基于关键词和当前结果回答“哪个结果最相关”“帮我比较这些结果”。
- **上下文可见**：AI 面板顶部显示当前引用的帖子、评论或搜索关键词，用户可以移除引用再继续问。
- **上下文不可信**：帖子和评论内容只作为待分析资料，不得覆盖系统规则或诱导 AI 执行无关操作。
- **返回可行动结果**：回答应尽量附带相关帖子、资料、活动或下一步按钮。

## 13. 学生端、管理端与后端协同架构

### 13.1 三层职责

SURF Campus 不是只有一个学生前台。产品由学生端、管理端和后端共同构成：

| 层级 | 面向谁 | 负责什么 | 不应承担什么 |
|---|---|---|---|
| 学生端 `frontend/` | 学生 | 完成查看通知、找资料、提问、报名、组队和社区互动等校园任务 | 直接修改全局数据、审核内容或管理他人权限 |
| 管理端 `admin/`（新增） | 平台管理员、教师/助教、活动组织者、就业办与审核人员 | 发布、审核、处理报名、维护资料与通知，并查看本职责范围内的运营状态 | 直接绕过权限修改 JSON、读取无授权的私人内容 |
| 后端 `backend/` | 前后端与 AI 服务 | 身份和权限校验、业务规则、数据读写、审计记录、API 输出与 AI 安全边界 | 把业务判断分散到前端，或把管理能力暴露给未授权用户 |

学生端和管理端都是前端界面，但服务不同角色、走不同权限的 API。两者只通过后端读写数据；前端不得直接编辑 `backend/data/*.json`。JSON 仅是当前 MVP 的 Mock 存储，后续由数据库和文件存储替换。

### 13.2 当前实现与必须补齐的缺口

当前项目已有学生端 `frontend/`、FastAPI 后端 `backend/main.py` 和 JSON Mock 数据，已经能读取通知、资料、问答、活动、帖子等数据；但还**没有管理端界面、管理员身份、权限校验、后台 API 命名空间或审计记录**。目前的公开 API 不能被视为正式后台能力。

因此，任何管理端功能必须按以下链路建设，而不是只增加一个静态页面：

```text
管理端操作
-> /api/admin/* 受权限保护的接口
-> 后端校验角色、参数和业务规则
-> 数据层保存内容与状态
-> 写入审计记录
-> 学生端读取已发布/已审核的数据并展示结果
```

### 13.3 管理角色与权限边界

第一版采用最小可用的角色模型，先以 Mock 登录和角色守卫验证路径，P3 再接入真实 XJTLU 身份认证和细粒度权限：

| 角色 | 可以管理 | 明确限制 |
|---|---|---|
| 平台管理员 | 账号与角色、全局通知、内容审核、违规处理、系统配置、审计记录 | 不能把匿名身份直接暴露给普通运营人员 |
| 教师/助教 | 自己课程的资料、课程问答、课程通知 | 不能修改其他课程或处理全站用户权限 |
| 活动组织者/就业办 | 自己组织的活动、报名名单、科研/志愿者/助理招募 | 不能访问无关活动或私人聊天内容 |
| 内容审核员 | 举报队列、树洞和社区内容的审核状态 | 仅在被授权的处理流程中访问追溯信息 |

所有管理操作都必须显示操作者、时间、对象、变更前后状态和处理理由。删除、封禁、隐藏和导出等高风险操作需要明确确认、可追溯记录，并尽量提供撤销或恢复路径。

### 13.4 管理端产品结构

管理端采用高密度、任务导向的运营工作台，不复用学生端的信息流布局。第一屏应优先展示待处理事项，而不是装饰性数据大屏：

```text
左侧：概览 / 通知 / 课程资料与问答 / 活动与招募 / 内容审核 / 用户与权限 / AI 知识与安全 / 审计记录
顶部：全局搜索、当前角色、待处理数量、个人菜单
主区：当前队列或列表 -> 详情抽屉/页面 -> 明确操作 -> 结果反馈
```

管理端 P0 必须同步交付的四条闭环：

1. **通知管理**：创建、分类、定时/立即发布、置顶、撤回和发布状态；已发布通知在学生工作台可见。
2. **课程资料与问答管理**：添加/编辑资料元数据、控制可见范围、处理待回答问题、标记教师/助教回答；学生端能搜索和查看发布结果。
3. **活动与招募管理**：创建、编辑、发布/下线活动，查看报名状态；后续扩展到科研和志愿者招募。
4. **内容审核基础**：查看举报、做出保留/隐藏/处理决定、记录理由和状态；前台用户看到对应处理反馈。

用户与权限、AI 知识来源、审计记录需要从 P0 建立数据模型和入口，可随 P1/P3 完善界面和真实权限，不允许等到学生端完成后再倒推。

### 13.5 前后端同步开发规则

每一个影响学生端的信息类功能都要同时回答“谁发布、谁维护、谁审核、谁处理异常”。开发顺序为：

1. 明确学生端用户路径和管理端责任人。
2. 定义共享的数据字段、状态机和权限规则。
3. 实现后端业务服务与学生端 API、管理端 `/api/admin/*` API。
4. 同步实现学生端结果展示和管理端操作界面。
5. 用“管理端创建/处理 -> 后端保存/审计 -> 学生端看到正确结果”的端到端路径验收。

例如，通知不是学生端写一个卡片就完成，而是：管理员发布通知 -> 后端记录类型、优先级、受众和状态 -> 工作台按规则展示 -> 学生标记已读或稍后处理 -> 管理端能看到发布及处理状态。
