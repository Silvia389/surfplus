# SURF Campus 产品缺口分析

> 分析日期：2026-08-02
> 资料来源：`数据/问卷AI-报告md.md`、`数据/原始表格数据汇总.xlsx`、`数据/线上采访结果汇总.xlsx`、`数据/默认问卷报告.pdf`、当前前后端实现

## 结论摘要

当前软件已经覆盖了信息流、通知、课程资料与问答、活动、组队、通讯录、匿名树洞、举报审核、聚合搜索和 AI 入口，作为 P0 可运行原型已经具备完整外壳。但研究数据表明，用户真正愿意持续使用的原因会集中在“更快找到可靠信息”和“更容易找到合适的人”，所以现在最大的风险不是再增加页面，而是把已有能力变成可信、可检索、可持续运营的闭环。

## 研究证据

- 有效问卷 50 份，其中大一学生 37 人，占 74%；理工/计算机 25 人，占 50%。高年级、教职工和国际生样本偏少，结论需要后续补样。
- 35/50（70%）认为信息分散，需要在多个平台切换。
- 20/50（40%）找不到学习资料或历史信息；21/50（42%）难以找到队友或学习伙伴；24/50（48%）担心重要通知被淹没。
- 最希望完成的场景是找资料 37/50（74%）、找队友 32/50（64%）、向老师/助教/前辈提问 29/50（58%）、获取通知 27/50（54%）。
- 学术讨论区与师生互动区均为 4.26/5，组队功能 4.22/5；界面清晰易懂 4.40/5，找到信息不费力 4.36/5。
- 40% 会因为广告泛滥放弃平台，24% 会因为卡顿或闪退放弃，20% 会因为社区氛围差放弃；39/50 对广告完全不接受或不太接受。

## 当前已经符合期望的部分

1. 首页已使用文字优先的单列校园话题流，实名公共内容与匿名树洞保持分离。
2. 课程资料、课程问答、通知、活动、组队、搜索和 AI 入口已形成可演示的工作台骨架。
3. 公开内容有分区、标签、审核、举报和管理端接口；用户可通过手机号访问，再用学校身份解锁互动。
4. 本轮补齐了首次资料初始化、学校邮箱后缀限制、主题模式、树洞无类型选择和 Nodemailer 服务骨架。

## 仍然缺少或需要加强的功能

### P0：决定用户是否留下

| 缺口 | 影响 | 建议验收 |
| --- | --- | --- |
| 真实数据源与数据新鲜度 | 资料、课程、通知和活动仍主要是 JSON Mock，用户无法形成“这里的信息可信且最新”的预期 | 接入学校课程/通知/活动数据源，显示更新时间和来源，过期内容自动标记 |
| 资料可用性 | 当前能搜索和打开元数据，但缺少完整的文件预览、权限、版本、失效处理和下载统计 | 课程、学期、资料类型、版本、来源、更新时间可筛选；失效链接有恢复路径 |
| 问答质量闭环 | 有提问和回答入口，但还缺少采纳、可信身份、重复问题合并、引用资料和通知 | 支持教师/助教身份、采纳答案、来源引用、相似问题提示和回答通知 |
| 主动组队匹配 | 当前更像招募列表，缺少技能画像、匹配理由、申请状态和拒绝反馈的完整运营 | 用户可设置技能/年级/语言/时间，看到匹配理由并完成申请到组队的状态闭环 |
| 通知可靠性 | 现在有通知展示和状态，但缺少来源等级、去重、提醒渠道、DDL/考试日历和免打扰 | 重要通知置顶、来源可信、可加入日历、可设置提醒并记录已处理状态 |
| 账号与隐私边界 | 目前是 JSON 持久化和 Mock 会话，正式环境还需要数据库、会话安全、限流、审计和账号注销 | 生产环境切换数据库，验证码/会话/个人资料可审计、可过期、可删除 |

### P1：决定社区氛围和活跃度

| 缺口 | 影响 | 建议验收 |
| --- | --- | --- |
| 社区治理与申诉 | 举报接口存在，但缺少规则中心、处理时限、用户申诉、重复举报合并和处罚透明度 | 用户能看到举报状态和规则摘要，管理端能记录处理理由与申诉结果 |
| 关注与个性化推荐 | 当前偏好会影响排序，但没有关注人、课程、Tag、项目和通知源 | 至少支持关注 Tag/课程/项目，并能解释推荐来源 |
| 跨年级/跨专业发现 | 通讯录存在，但没有针对学习伙伴和项目伙伴的安全匹配流程 | 搜索或推荐结果显示共同兴趣、技能和匹配原因，不直接暴露不必要的联系方式 |
| 私聊安全 | 有私聊和项目群入口，但缺少拉黑、举报、陌生人消息控制和敏感操作提示 | 支持拉黑、举报、消息请求、项目群成员管理和撤回/删除策略 |
| 树洞安全体验 | 匿名发布已分离，但需要内容风险分级、危机提示、敏感信息提醒和后台追溯权限分离 | 发布前提示匿名边界，风险内容进入人工队列，管理员操作有审计 |
| 活动报名运营 | 活动列表和报名已有，但缺少候补、签到、取消截止时间、报名提醒和活动反馈 | 报名状态、名额、候补、提醒、签到和反馈可追踪 |

### P2：影响长期运营

- 完善移动端底部导航的信息密度、无障碍朗读、键盘操作和高对比度验证。
- 加入性能预算：首屏加载、图片/视频大小、接口响应时间、失败重试和离线/弱网状态。
- 去掉商业广告或建立严格的校园内容审核政策，因为研究中广告接受度明显偏低。
- 建立埋点和产品指标：3 分钟内完成首个任务、资料搜索成功率、问答采纳率、组队申请转化率、通知处理率、举报处理时长和 7 日留存。
- 补充高年级、研究生、教职工、国际生和非理工专业的访谈，避免产品只优化大一理工学生。

## 推荐下一步

1. 先接入一套可信的课程/通知/活动数据源，并给每条信息加来源和更新时间。
2. 把课程问答和组队从“能发”推进到“有状态、有反馈、有可信身份”。
3. 建立生产级数据层、会话安全和内容治理，再接真实学校邮箱/SSO。
4. 用 8-12 名不同年级与专业学生做一次任务测试，观察找资料、找队友、看通知三个任务是否能在 3 分钟内完成。

## 当前判断

本项目不是缺少更多入口，而是缺少可信数据、持续运营和高信任闭环。下一轮优先提升“信息可用性”和“匹配成功率”，比继续增加新模块更符合 2026 年 6 月问卷与访谈呈现出的用户期待。
