## 重要范围：学生端、管理端和后端必须一起做

本项目不只重做学生端 `frontend/`。必须同步建设：

- **学生端 `frontend/`**：学生浏览单列校园话题流，按分区、标签和聚合搜索发现相关议题，发布文字、图片和视频内容，并完成通知、资料、问答、活动、组队和社区等校园任务。
- **管理端 `admin/`（必须新增）**：给平台管理员、教师/助教、活动组织者/就业办、审核人员使用，管理通知、课程资料与问答、活动与招募、举报审核、用户与权限、AI 知识来源和审计记录。
- **后端 `backend/`**：负责 API、角色权限、业务规则、数据读写和审计。现有 `backend/data/*.json` 仅是 Mock 数据，前端不得直接修改。

正式闭环必须是：

```text
管理端操作
-> /api/admin/* 受权限保护的后端接口
-> 后端校验、保存数据并记录审计
-> 学生端读取已发布/已审核的数据
-> 用户完成操作并得到反馈
```

管理端不是一个静态展示页面。至少要真实跑通：通知发布/置顶/撤回、资料与问答管理、活动发布与报名管理、举报处理与状态反馈。学生端每增加一个信息类功能，都要同时明确谁在管理端发布、维护、审核和处理异常。

首页必须以**单列校园话题流**作为主要内容，文字帖子优先，图片和视频作为可选附件。内容按学术、校园生活、活动与机会、组队与项目等受控分区组织，支持标签、标签聚合页和全局聚合搜索。帖子发布、媒体上传、浏览、举报和审核要与管理端、`/api/admin/*` 和后端媒体数据同步实现。

## 开发约束

- 从 `TODO.md` 当前 P0 主线的第一项未完成任务继续，不擅自跳到后续阶段。
- 遇到技术或实现问题，先读代码、数据、日志、API 和文档后自行处理；只有需要产品取舍、存在隐私/安全影响、会进行不可逆操作或现有证据无法判断时才询问用户。
- 用户需求含糊时，优先依据当前对话要求、`PROJECT_PLAN.md`、`数据/` 的问卷与访谈、`TODO.md` 和现有代码/API 做低风险、可回退的推断。
- 所有界面、组件、交互和动效工作必须使用 Apple Design 与 Emil Kowalski / Design Engineering Skill；旧 Demo 的模板化视觉和交互不能作为新版本基础。
- 管理端操作统一走 `/api/admin/*`；先实现 Mock 登录和角色守卫，再在 P3 接入真实 SSO、数据库和细粒度权限。
- 不覆盖用户已有的未提交修改；改动后运行相应检查，并更新 `TODO.md` 的验证记录。

## 应该选择哪种模式

### 真正开始开发、运行和验证时：选择目标/执行模式

如果界面把正常执行称为“目标模式”，选择它。当前 Codex 环境里对应的是 **Default / 正常执行模式**。适用于修改前后端、构建管理端、启动服务、调用 API、运行测试和检查页面。

### 只想先讨论路线时：选择计划模式

选择 **Plan mode** 的场景是：只想看现状、比较方案、拆解任务或确认范围，暂时不希望修改代码。计划确认后，切回目标/执行模式，并明确说“按计划开始执行”。

如果目标已经清楚，直接使用目标/执行模式，不必再生成一次计划。

## 本项目目标模式目标说明

需要让下一个 AI 直接执行本轮 P0 时，使用下面这段作为 Goal：

```text
目标：在 /Users/hanmingyu/Desktop/surf项目 持续推进 SURF Campus 的 P0 重建，完成一个可运行、可验证的“文字优先校园话题首页 + 内容发现 + 管理闭环”，不要只输出计划或静态页面。

先阅读：
- surfplus/surf-campus/START_HERE.md
- surfplus/surf-campus/PROJECT_PLAN.md
- surfplus/surf-campus/TODO.md
- 数据/ 下的问卷、访谈和分析材料
- 当前任务相关的 frontend/、admin/、backend/、agent/ 代码及工作区改动状态

必须完成的产品方向：
1. 首页主体是单列校园话题流，不使用工作台卡片墙或双列瀑布流作为首页主形态。桌面端使用舒适阅读宽度的主流和通知/热门标签侧栏，移动端保持单列连续阅读。
2. 发帖器以文字输入为默认方式，同时支持纯文字、图文和视频帖子。图片要有预览、排序、删除、上传进度、失败重试和详情查看；视频要有封面、时长、加载、播放/暂停、静音和失败状态。
3. 帖子必须分为受控分区：学术、校园生活、活动与机会、组队与项目；匿名树洞独立处理，不默认混入实名公共内容流。
4. 每篇帖子支持 0-5 个 Tag。提供课程、活动、技能、地点、议题等推荐 Tag，并对自定义 Tag 做规范化和审核。用户点击 Tag 后，进入 Tag 聚合页，看到相关帖子、课程问答、资料、活动和相关 Tag。
5. 实现聚合搜索：搜索帖子标题/正文/Tag/分区、课程资料、课程问答和活动；结果支持按内容类型和分区筛选，并能从关键词继续探索相关议题。
6. 学生端 frontend/、管理端 admin/、后端 backend/ 同步建设。管理端是必做项，不是后续补充。
7. 管理端至少能管理帖子和媒体审核、分区与 Tag、通知、课程资料与问答、活动和举报；后端提供受权限保护的 /api/admin/* 接口、Mock 登录/角色守卫、状态保存和审计记录。
8. 前端不得直接修改 backend/data/*.json；P0 可使用本地开发媒体存储，后续再替换正式对象存储。

实现标准：
- 所有界面、组件、交互和动效使用 Apple Design 与 Emil Kowalski / Design Engineering Skill。
- 旧 Demo 的模板化视觉、组件和交互全部推翻重建。
- 遇到问题先自行阅读代码、日志、接口、数据和文档并解决；需求不确定时依据当前要求、PROJECT_PLAN.md、数据/研究材料、TODO.md 和现有 API 做低风险推断。
- 以完整闭环为验收标准：发布/上传 -> 后端保存 -> 管理端审核 -> 首页展示 -> Tag 聚合/搜索 -> 帖子详情与互动。
- 同时检查加载、空数据、错误、成功、禁用、权限拒绝、媒体失败、桌面端和移动端状态。
- 不覆盖已有未提交修改，不伪造数据或验证结果。

执行顺序：先检查现状和 TODO 的第一项未完成任务，再以最小可运行垂直切片推进；每完成一个切片立即运行验证并更新 TODO.md。最终汇报修改文件、学生端/管理端/后端闭环、验证结果、遗留风险和下一步。
```
